## 1. 꼭 기억해야 하는 것

### 1-1. 색인 문자열이 바뀌면 **기존 DB를 다시 만들어야 한다**

이번에 색인에 한글 바이그램이 들어갔다. 그런데 **이미 만들어진 DB는 옛 색인을 그대로 들고
있어서, 고친 검색이 전혀 반영되지 않는다.** 실제로 노트북에서 이것 때문에 "고쳐도 여전히
0건" 으로 보였고, DB를 지우고서야 동작을 확인했다.

- **노트북**: `build/hjp-desktop.db` 를 지우면 된다
- **앱**: `MIGRATION_4_5` 가 색인만 비우고, `RoomBusinessCardRepository.seedIfEmpty()` 가
  `countFts() == 0` 을 보고 코틀린으로 다시 채운다

색인 문자열을 만드는 규칙은 **`SearchIndexText` 한 곳에만** 둔다. 마이그레이션 SQL 로
채우지 않는 이유가 이것이다 — 규칙이 두 벌이 되면 반드시 갈라진다.

`HjpDatabaseV5MigrationInstrumentedTest`가 Android에서 합성 v4 DB를 열어 실제 4→5
마이그레이션 경로를 태웠다. 카드 보존, 구 FTS 삭제, 저장소의 자동 재색인과 `판교역로` 검색을
확인했다. 사용자 폰의 실제 장기 사용 DB로 하는 최종 스모크 테스트만 남았다.

### 1-2. gradle 증분 패키징이 옛 자산을 들고 있는다

KIE 모델을 86MB 작은 것으로 바꿨는데 **APK 크기가 바이트 단위로 그대로였다.** 자산은 바뀌었고
빌드도 성공했는데 패키징이 옛것을 재사용했다. `--rerun-tasks` 로 재패키징해야 반영된다.

자산 파일을 바꾼 뒤에는 APK 크기나 내용물을 반드시 확인할 것.

### 1-3. 노트북 러너로는 못 잡는 결함이 있다

OpenCV `imread` 는 EXIF 를 존중한다. 그래서 **회전 문제는 러너에서 재현되지 않았고**,
안드로이드의 `BitmapFactory` 경로만 깨져 있었다. 러너가 이 결함을 못 잡은 이유다.

| | 노트북 러너 | 에뮬레이터 | 실기기 |
|---|---|---|---|
| OCR 인식·KIE·그룹화 | O | O | O |
| 검색·멀티턴 규칙 | O | O | O |
| EXIF 회전 / 촬영 | **X** | O | O |
| Gemma 답변 생성 | X | X | O |
| 의미검색(벡터) | X | X | O |

### 1-4. 코드 대조만으로는 안 나오는 결함이 있다

이번에 찾은 것 중 둘은 **파일·함수 목록 비교로는 전혀 안 보였다**:

- 방향 분류기가 이름을 뒤집던 것 → 글자 크기를 바꿔 가며 **재봐야** 나왔다
- 공백이 사라지던 것 → 파이썬 참조 구현과 **실제로 대조해야** 나왔다

원본 App 트랙에 `ref_pipeline.py`(순수 ONNX 참조 구현)가 있다. 우리 모델을 물려 같은
이미지를 돌리면 이식본과 직접 대조할 수 있다. **OCR 을 건드렸으면 이걸 돌려 볼 것.**

### 1-5. 모델 파일의 짝

`kie_minilm_int8.onnx`(36.6MB)와 `kie_tokenizer.onnx`(0.85MB)는 **한 벌이다.** 분류기의
임베딩 행 번호가 곧 토크나이저가 내놓는 id 라서, 섞으면:

- 옛 토크나이저 + 새 분류기 → id 범위 초과로 **예외가 나서 걸린다**
- 새 토크나이저 + 옛 분류기 → id 가 범위 안이라 **그냥 돌고 결과만 엉킨다** ← 위험

토크나이저는 저장소에 있고 분류기(36.6MB)는 손으로 넣는 파일이라 후자가 실제로 일어날 수
있다. 그래서 `KieParser` 가 시작할 때 `"010-1234-5678" → mobile` 을 넣어 보고, 틀리면
KIE 를 쓰지 않고 `CardParser` 휴리스틱으로 내려간다.

### 2-5. 방향 분류기가 멀쩡한 이름을 뒤집던 것 (`f1fd0a8` → `d2cd172`)

`f1fd0a8` 로 넣은 분류기가 **이름을 망가뜨리고 있었다.** "남다은" 이 "긍그" 로 읽혔는데,
처음에는 rec 의 한계로 보고 넘어갔다(**오판이었다**).

숫자가 알려줬다 — `80` 이 `08` 로, `68` 이 `89` 로. 읽는 순서가 뒤집힌 모양이다.

크기가 아니라 **길이**가 문제였다. 똑바로 선 크롭의 P(180) — 낮아야 맞는 값:

| 가로세로비 | 글자수 | P(180) | |
|---|---|---|---|
| 1.07 | 1 | 0.752 | 틀림 |
| 2.74 | 3 (`남다은`) | 0.866 | 틀림 |
| 3.58 | 4 | 0.893 | 틀림 |
| 5.26 | 6 | 0.609 | 틀림 |
| 5.56 | 7 | 0.001 | 맞음 |
| 12.51 | 17 | 0.000 | 맞음 |

긴 글줄에서 0.001 대 0.999 로 깨끗하게 갈리므로 전처리는 맞다. 모델이 짧은 크롭에 약한
것이고, **그건 신뢰도로 거를 수 없다 — 틀린 답이 0.9 로 확신에 차 있다.** 처음에 둔 신뢰도
임계값(0.6)이 아무 소용 없던 이유다.

→ 가로세로비 6 이상에서만 묻는다(`TextLineOrientation.MIN_ASPECT`).

### 2-6. 인식된 공백이 전부 사라지던 것 (`fc7bc78`)

파이썬 참조 구현과 대조하다 찾았다. 영역 수·글자·점수(±0.03) 다 같은데 **공백만 달랐다**:

```
참조:  "경기도 성남시 분당구 판교역로 123"   "너울건설 상무"
이식본: "경기도성남시분당구판교역로123"      "너울건설상무"
```

`charset` 은 blank + 사전 + 공백 순서인데,

```
파이썬 "가\n나\n".splitlines()    -> ["가","나"]
코틀린 "가\n나\n".lineSequence()  -> ["가","나",""]     <- 끝에 빈 항목
```

사전 파일이 개행으로 끝나므로 빈 항목이 하나 끼고, 그 한 칸이 **공백 문자의 번호를 밀어낸다.**
모델이 공백을 가리키면 빈 문자열을 꺼내 왔다.

**FTS 는 공백에서 자른다.** 촬영 저장한 명함의 주소가 통째로 낱말 하나가 되어, 나중에
"판교" 로도 "성남" 으로도 안 잡힌다 — §2-2 에서 고친 문제를 데이터 쪽에서 되살리는 셈이다.

### 2-7. KIE 모델 어휘 축소 (`bff6596`)

분류기 113MB 중 **96MB 가 임베딩 테이블 하나**였다(250,037 × 384 int8). XLM-R 의 다국어
어휘인데, 250,002 조각 중 **82,818 개가 ASCII 여러 글자 조각** — 유럽어 단어용이라 한국어
명함 필드 분류에는 쓰이지 않는다.

```
kie_minilm_int8.onnx   113 MB -> 36.6 MB   (임베딩 250,037 -> 37,258 행)
kie_tokenizer.onnx     4.9 MB -> 0.85 MB
APK                    416 MB -> 330 MB
```

**압축이 아니라 안 쓰는 어휘를 잘라낸 것**이라 성능은 보존된다. 텐서를 직접 대조해 확인했다:
분류기 헤드와 인코더 130개가 **비트 단위로 동일**하고, 다른 6개는 position/token_type
임베딩의 양자화 차이뿐(역양자화 후 최대 0.0046).

합성 문장 19개 대조에서 17개 일치. 갈린 둘:

- `南多恩` : `name_hanja` → `logo_text` — **실제 손실**. 축소 규칙이 "여러 글자 조각은 한글이나
  ASCII 가 끼어 있어야" 인데 한자는 거기 없다. **한자 이름을 쓰지 않기로 해서 그대로 둔다**
- `함께 만드는 내일` : `company_ko` → `slogan` — 축소본이 더 정확하다

### 2-8. `:desktop` 을 저장소에서 제거 (`a066255`)

## 3. 남은 것

### 3-1. 실기기 확인 (가장 중요)

폰이 계속 adb 에서 떨어져 있어 못 했다. 확인해야 할 것:

| 항목 | 왜 실기기여야 하나 |
|---|---|
| **색인 마이그레이션 실DB 스모크** | 합성 v4→v5 경로는 통과. 실제 사용자 DB 백업본으로 마지막 확인 필요 |
| Gemma 답변 생성 | arm64 전용 |
| 의미검색(벡터) | arm64 전용 |
| 메일·일정 도구로 턴이 안 죽는지 | §2-1 의 원래 증상 |

추가 점검에서 ryeong의 `seedEmbeddingsFromAsset()` 이 통합 중 빠져, APK에는 1000장 벡터가
있지만 런타임은 전혀 읽지 않는 누락을 찾았다. `BundledCardEmbeddings`로 복원했고 카드 지문,
ID/벡터 SHA-256, 개수·크기를 확인한 뒤 **카드 시드와 동시에** Room 기본 색인으로 넣는다.
이미 카드만 존재하는 DB도 벡터 1000개를 복구한다. Android 에뮬레이터에서 시작 시 1000건,
신규 명함 +1, 명함 수정 직후 기존 벡터 교체를 모두 검증했다. 채팅은 벡터 DB에 저장하지 않는다.
실제 쿼리 임베딩과 하이브리드 검색은 arm64 실기기 테스트가 남아 있다.

앱의 프로덕션 검색 배선에서도 키워드 폴백을 제거했다. EmbeddingGemma가 없거나 초기화·추론에
실패하면 검색을 중단하며, 이메일·전화번호 같은 식별자 질의의 의도적 의미검색 제외만 별도다.
통합 완료 판정에서도 모델 폴백을 허용하지 않는다. `install_real_device_debug.ps1`가 필수 모델
3개의 로컬/기기 해시를 확인하고 생성·의미검색·OCR/KIE 계측 테스트를 실행하며, 하나라도
없거나 로드되지 않으면 skip하지 않고 중단한다. 에뮬레이터 결과는 보조 검증일 뿐이다.

확인 방법 — 디버그 주입구로 사람 손 없이 태울 수 있다:

```bash
adb shell am start -n com.example.hjp/.MainActivity --es q "판교개발자"
adb shell am start -n com.example.hjp/.MainActivity \
    --es test_image_path /sdcard/Android/data/com.example.hjp/files/card.jpg
adb logcat -s HJP:I HjpContactSearch:I
```

> 이미지는 `/sdcard/Download` 가 아니라 **앱 자기 폴더**에 넣어야 한다
> (Android 13+ 범위 저장소라 권한 없이 못 읽는다).

### 3-2. `search-core` 외부 평가 입력 — 해결됨
