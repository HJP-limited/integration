# OCR 원본 Android 경로 복원

기준: `HJP-limited/HJP_limitededition`, `r1_phase2_sprint_c`, `010d3b1344b6083c45507ac9866919d5d87808c9`.
`OCR/demo.py`는 CLI이고 실제 Android 기준 코드는 `App/android`에 있다.

## 수정

- 세로 글줄 크롭을 원본과 같은 시계 방향 90도로 복원했다.
- 원근 보정도 원본 Android의 기본 보간/테두리 처리로 복원했다. 통합본의 `INTER_CUBIC/BORDER_REPLICATE` 변경을 제거했다.
- 원본 Android의 `cropQuad → recognize` 사이에 통합 과정에서 추가했던 0/180 보정을 제거했다.
  기존 필수 `textline_ori` 파일은 계속 포함·로드 검사하지만, 원본에 없는 인식 단계를 실행했다고 표시하지 않는다.
- `OcrImageLoader`에 원본과 같은 2000px 다운샘플·소프트웨어 비트맵·EXIF 디코딩 경로를 분리했다.
  반사 EXIF 지원은 유지한다. 읽기/보정 실패 시 보정 전 사진으로 조용히 진행하지 않는다.
- 원본 Manifest의 `orientation|screenSize` 처리를 복원하고 촬영 URI·선택 이미지·수동 회전 상태를 저장 가능하게 했다.
- 촬영/갤러리 선택 후 미리보기에서 방향을 확인하고 `이 방향으로 인식`을 누른다.
  EXIF가 정상이라고 기록됐지만 내용이 누운 사진은 `오른쪽으로 90° 회전`으로 직접 조정한다.
  미리보기·OCR 입력·결과 오버레이가 같은 비트맵을 사용한다.
- 미리보기 회전 기능은 원본 자체의 기능이 아니라 사용자가 보고한 촬영 파일을 위한 명시적 보완이다.
  전체 사진 방향을 자동 추론한다고 주장하지 않는다.
- 통합앱의 KIE 필드 묶기·명함 저장/임베딩 연결과 필수 모델 누락 차단은 유지한다.

## 비교 검증

원본 OCR/후처리 코드를 계측 테스트 전용 패키지에 고정했다. 원본 변경은 패키지명·자산 접두어·자원 해제뿐이다.
실제 촬영 파일이 없으면 테스트는 중단한다. 원본과 통합 디코딩 픽셀을 비교하고,
원본 사진 및 명시적 90도 회전 사진의 검출 수·텍스트·좌표·점수를 비교한다.
사용자 사진은 Git에 넣지 않는다.

- 전체 단위 테스트 564개, 실패/오류/건너뜀 0.
- 앱 및 계측 APK 빌드 성공: `build/ocr-parity-final-build.log`.
- 실기기 비교 결과는 `build/ocr-upstream-device-test.log`, `build/ocr-upstream-device-detail.log`에 기록한다.
- 첫 실기기 비교에서 픽셀 회전 검사는 통과했으나 원근 보정 차이 때문에 OCR 점수 불일치를 발견했다.
  실패 증거는 `build/ocr-upstream-device-test-before-warp-fix.log`에 보존했다. 허용 오차를 넓히지 않고 원본 크롭 구현을 복원했다.

최종 S21 재검증: **OK (2 tests)**, 26.093초.
실제 사진의 원본/통합 디코딩 픽셀 일치, 원본 방향과 시계 90도 회전 방향의 검출 수/텍스트/좌표/점수 일치,
EXIF 및 수동 회전 픽셀 기하 검사를 통과했다. 이번 사진 두 방향에 대한 비교이며 전체 데이터셋의 OCR 정확도 보증은 아니다.
이 비교는 det/rec/후처리 동등성 검사다. KIE는 실제 로드/실행하지만 원본과의 필드 묶기 동등성을 별도 판정한 것은 아니다.
앱은 `install -r`로 업데이트했으며 기존 다운로드 모델과 촬영 파일을 보존했다.
사용자의 재촬영 및 나머지 통합 검증이 이어지는 동안 앱을 유지하고, 전체 실기기 테스트 종료 후 삭제한다.
