# 현재 165개 시나리오와 앱 실행 연결

## 버전 정정

- `app/src/test/resources/ryeong/scenarios_v1.json`: 과거 130개/377턴 스냅샷.
- 같은 폴더의 `scenarios_v2.json`: 과거 139개/386턴 스냅샷.
- **현재 기준**: `scripts/eval_multiturn.py`의 `build_scenarios(..., scenario_set="v1")`.
  `data/cards_eval1000.json`, RNG seed 42 기준 **165개/435턴/27유형**이다.
- 위 파일 이름의 v1/v2와 현재 생성기의 v1/v2는 같은 버전 구분이 아니다.
  구버전 JSON이 호출되지 않는 것만으로 현재 165개 평가가 누락됐다고 판단한 것은 잘못이었다.
- 현재 Python 평가는 `hybrid_server :8100`과 노트북 LLM 서버를 호출한다. 그 결과를
  통합앱 AgentKernel 실행 결과로 간주할 수는 없어, 이번에 별도 앱 재생 경로를 추가했다.

## 실행

```powershell
# 현재 생성기에서 시험지 갱신. 모델 추론을 수행하는 명령은 아니다.
python scripts/export_multiturn_app_suite.py
python scripts/export_multiturn_app_suite.py --check

# arm64 테스트폰 연결 후, 모델 검증·필수 스모크·165개 전체 재생
.\scripts\install_real_device_debug.ps1 -RunMultiturn165
```

기본 설치 명령에는 장시간 전체 재생을 강제로 넣지 않았다. 위 옵션을 주면
`CurrentMultiturn165InstrumentedTest`가 테스트 APK의 `multiturn/current_165.json`을 읽고
통합앱의 실제 `container.engine`을 실행한다. JVM 로컬 파서로 대체하지 않는다.

- 165개 모두 실행하며 `known_gap`·`generate_only`를 이유로 제외하지 않는다.
- 시나리오 사이에는 세션을 초기화하고, 시나리오 안의 턴은 순서대로 이어간다.
- 사용자 승인 요청에는 자동 거절하여 테스트가 명함 수정을 승인하지 않도록 한다.
  이로 인한 미완료는 실패 기록으로 남는다. 메일/일정 작성 화면이 열릴 수 있으므로 테스트폰을 사용한다.
- 턴별 시간 제한은 180초다. 일반적인 실패는 기록 후 다음 턴을 실행한다.
  필수 모델 누락/사용 불가, 전체 작업 취소는 남은 턴을 정상 실행처럼 채우지 않고 중단한다.
- 실기기·OCR/KIE·생성·임베딩 필수 게이트를 먼저 검사한다. 없는 모델을 skip하지 않는다.
- 진행: `adb logcat -s HjpMultiturn165`. 전체 실행은 장시간 걸릴 수 있다.

## 결과와 채점 범위

기기 `files/evaluation/multiturn-165-<timestamp>.jsonl`에 매 턴 flush한다.
설치 스크립트는 실패해도 `build/multiturn-165-evidence`로 증거를 회수하려 시도한다.
시작/종료 레코드의 실행 수와 `complete`를 함께 확인한다. 이전 실행 파일과 섞어 집계하지 않는다.

이 연결은 **전체 질문 실행 + 실제 답변 체크리스트 회귀 검사**다. 빈 답변·사용자 오류·예외·시간 초과,
원본 `must`/`must_not` 위반을 실패로 기록하고, 종료 시 하나라도 실패하면 테스트가 실패한다.
실제 모델 호출 여부도 확인한다. JSONL에는 원래 경로·슬롯·정답 ID·no_cards 기대값과
실제 검색 결과·선택 대상·후보·실행 도구·진단을 보존한다.

**Python의 경로 이름/JGA/Hit@5와 앱의 지표를 동일하게 환산한 것은 아니다.** 원본의 `search`가
앱에서는 결정적 `ContactDetail`일 수 있고, 검색 결과와 화면 표시 카드는 다를 수 있기 때문이다.
기존 Python 수치와 직접 비교하거나, 실행·체크리스트 성공을 모든 평가 축의 통과라고 보고하지 않는다.
앱 UI 자체의 카드 표시·버튼 조작까지 자동화한 테스트도 아니다.

질문과 정답을 통과시키기 위해 바꾸지는 않았다. 과거 평가가 기대하는 동작과 현재 안전 정책이
충돌하면 원본 기대값과 실제 동작을 보고 정책/시험지 버전을 별도로 결정해야 한다.

## 확인 상태

현재 라우터에서 별도로 확인한 두 결함도 수정했다. 과거 시나리오 파일 여부와 무관한 실제 분기 문제다.

- `현수 아니고 허현`: 짧은 문장의 `아니고`를 반응으로 오판해 이전 답변을 재출력했다.
  이제 단독 반응/수량 정정만 재출력하며 이름 변경은 기존 대상 교체 경로로 전달한다.
- `그 사람들 중 서울 사람만`: 복수 지시어만 보고 무조건 이전 명단 전체를 반환했다.
  이제 단순 명단 재표시만 즉답하고, 조건 추가·작업 요청은 후보 메모리를 가진 정상 엔진에 전달한다.
  `방금 그 사람`이라는 단수 표현도 복수 명단으로 오인하지 않는다.

해당 회귀 검사는 라우팅을 검증한다. 실제 모델의 조건 필터링 정확도는 아래 기기 재생 결과로 확인해야 한다.

- 원본 생성기를 직접 호출해 165/435와 동결본 재생성을 확인했다.
- 시험지 무결성 JVM 검사는 모델 실행을 하지 않으며, 실제 모델 검증으로 집계하지 않는다.
- 2026-09-15: `test :app:assembleDebug :app:assembleDebugAndroidTest` 성공.
  JVM 526개, 실패/오류/스킵 0개. 이 숫자는 435턴 모델 실행 건수가 아니다.
- `adb devices -l`에 연결된 기기가 없어 실제 앱 재생은 미실행 상태다.
- 실제 435턴 실행은 필수 모델을 탑재한 arm64 기기가 필요하다. 실행하지 못한 상태를 통과로 표기하지 않는다.
