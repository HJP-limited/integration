# 노트북 웹 테스트 화면 — 2026-09-19

폰 없이 브라우저에서 같은 커널을 두드리기 위한 로컬 서버다. 실기기 검증을 대신하지 않는다.

## 실행

```powershell
.\scripts\run_desktop_web.ps1            # 빌드 후 http://127.0.0.1:8765
.\scripts\run_desktop_web.ps1 -SkipBuild # 최신 빌드가 있을 때
.\scripts\run_desktop_web.ps1 -Port 9000 -Yes
.\scripts\run_desktop_web.ps1 -Rules     # 규칙 게이트웨이(모델 품질 검증 아님)
```

## 통합 후 실제 HTTP/SSE 회귀 검사

실제 모델 서버를 실행한 상태에서 다른 터미널로 실행한다. Python 표준 라이브러리만 사용한다.

```powershell
python scripts/check_desktop_web.py --log build/web-integration-turns.jsonl
# 다른 포트로 실행했다면:
python scripts/check_desktop_web.py --url http://127.0.0.1:8876 --log build/web-integration-turns.jsonl
```

이 검사는 서버의 실제 Gemma 해시·ONNX 임베딩·기본 명함 1,000장을 확인하고,
`eval/web_integration_regressions_2026-10-04.json`의 성씨 검색 → 첫 후보 선택 → 문지영 전화번호와
기존 문자 → 검색 → 일정 → 검색 → 명함 수 5턴을 HTTP/SSE로 실행한다.
현재 턴의 완료·실패 여부, 실행 도구, 반환 ID, 이전 후보 선택 ID, 성씨·직업 근거,
검색 결과 밖의 인물 혼입, 모의 초안 여부를 판정한다. `--rules` 서버는 통과하지 않는다.
각 suite 시작 시 서버 대화를 초기화한다. 테스트 DB를 분리하려면 서버 실행 전에
`HJP_DESKTOP_DB`를 별도로 지정한다.

정확한 필드 조회를 Gemma 추론 성공 횟수로 집계하지 않는다. 외부 앱 호출은 SIMULATED이며
HTTP/SSE 통과는 Android 화면·기기 런타임·실제 전송/일정 저장 검증이 아니다.

서버가 도는 동안 `:desktop:installDist` 를 따로 실행하지 않는다. JAR 을 덮어써서 실제로
`ClassNotFoundException` 이 났던 적이 있다. 127.0.0.1 에만 바인딩한다 — 같은 네트워크의 다른
기기에서는 열리지 않는다.

## 무엇이 앱과 같고 무엇이 다른가

같은 것: `AgentKernel`·`DeterministicTurnRouter`·`AgentWorkflowPolicy`·도구 계약·검증,
`SearchLookupService` 검색 경로, 명함 시드 1,000장, Gemma 아티팩트 파일
(`gemma-4-E2B-it.litertlm`, SHA-256 검증 통과), OCR·KIE 모델 파일.

다른 것:

- 실행 런타임이 PC 의 Python LiteRT-LM 이고 Android 는 0.16.1 이다.
- 임베딩이 PC 는 ONNX, Android 는 TFLite 다. 같은 모델의 다른 내보내기다.
- 메일·문자·일정은 초안까지만 만들고 외부 화면을 열지 않는다(SIMULATED). 화면에 그 초안을
  그대로 보여 주므로 수신자·본문은 확인할 수 있지만, 실제 앱 실행·전송을 검증한 것이 아니다.
- 촬영 화면·권한·다운로드는 여기에 없다.

같은 문장을 화면 상단과 `/api/status` 가 함께 쓴다. 화면을 캡처해 "폰에서 됐다"로 쓰지 않는다.

## 화면

- **대화**: 질문을 보내면 도구 진행이 실시간으로 뜨고, 턴이 끝나면 실행 도구 연쇄·명함 ID·
  소요 시간·모의 초안이 함께 남는다. CLI `turn` 이 찍는 증거와 같은 값이다.
  `새 대화` 는 커널 세션과 네이티브 대화를 함께 초기화한다.
- **명함 인식**: 사진을 올리면 앱과 같은 검출·인식·KIE 로 필드를 뽑는다. `DB에 저장` 을 켜면
  `S###` 로 저장하고 이름 색인과 임베딩을 즉시 다시 세운다(앱이 저장 직후 하는 일과 같다).

## 경계

`desktop/src/main/kotlin/com/example/hjp/desktop/WebServer.kt` — HTTP 경계만 새로 만든 것이고
에이전트는 `turn` 이 쓰는 `DesktopAgent` 를 그대로 연다. 화면 HTML 은
`desktop/src/main/resources/web/index.html` 이며, 소스 파일이 있으면 그쪽을 먼저 읽으므로
빌드 없이 새로고침만으로 고칠 수 있다.

엔드포인트: `GET /api/status`, `GET /api/turn?text=`(SSE), `POST /api/reset`,
`POST /api/ocr?save=`(이미지 바이트).

## 이번에 확인한 것

- 상태: 모델 `KNOWN_ARTIFACT_VERIFIED`, SHA-256 일치, 명함 1,000장.
- `문지영씨 전화번호` → `get_contact` / `T002` / 54ms / `010-3001-6001`.
- `데이터분석가 누구 있지` → `search_contacts` / 5건(T037, S04884, S00991, S03130, S03139) / 29.1초.
- OCR 업로드 경로: 이미지 디코드와 검출·인식·KIE 로드까지 동작(빈 이미지 0영역, 137ms).

확인하지 않은 것: 실제 명함 사진의 인식 품질, 실기기 동등성, 메일·문자·일정의 실제 실행.

원격의 수정 실패 복구 계약을 통합한 뒤, 노트북 SQLite 저장소도 `restore`를 구현했다.
재임베딩 callback이 실패하면 명함의 전체 이전 스냅샷과 FTS를 한 트랜잭션으로 복구한다.
`SqliteCardRollbackTest`는 실제 SQLite 파일을 다시 열어 값·타임스탬프·검색 색인이 복구됐는지
확인한다. 의도적으로 실패시킨 callback을 쓰는 제어 흐름 테스트이며 실제 모델 검증과 별도다.

## 주의

한글 질의를 셸에서 curl 로 보낼 때 코드 페이지가 UTF-8 이 아니면 질의가 깨진 채 모델까지
간다(실제로 겪었다). 브라우저는 UTF-8 로 인코딩하므로 화면에서는 문제가 없다. 스크립트로
때릴 때는 UTF-8 퍼센트 인코딩을 직접 확인한다.
