# 파이프라인 후속 점검 및 앱 내 모델 다운로드

기준 커밋 `9c378a0` 이후의 작업이다. 이전 점검의 제품 파일 대조 결과를 반복 집계하지 않고,
OCR 저장 이후 검색 갱신, 검색 중 동시 변경, 모델 설치, 선택 대상의 멀티턴 전달 경계를 점검했다.
사용자가 보고한 실제 실패 문장·실기기 로그는 아직 제공되지 않아 그 현상을 재현했다고 주장하지 않는다.

## 모델 다운로드

설정 → 모델 파일 관리 → 이용 조건 확인·동의 → Hugging Face 읽기 토큰 입력 →
`필수 모델 다운로드 / 이어받기`로 임베딩·토크나이저·생성 모델을 받는다. 합계 약 2.8GB다.

- 토큰은 화면/진행 중 작업의 메모리에만 두며 파일·로그에 저장하지 않는다.
- Hugging Face 호스트에만 인증 헤더를 보내고 CDN 리디렉션에는 전달하지 않는다. HTTPS만 허용한다.
- 화면을 나가면 취소되므로 다운로드 동안 화면을 유지해야 한다. 백그라운드 서비스는 구현하지 않았다.
- `.part` 파일은 다음 시도에서 Range로 이어받는다. 서버의 범위와 파일 길이를 확인하며,
  끝까지 받은 뒤 SHA-256 검증을 통과한 파일만 원자적으로 설치한다.
- 파일 가져오기도 동일한 크기·해시 검증과 임시 파일 설치를 사용한다. 중단된 가져오기가
  기존 정상 모델 파일을 잘라 버리던 경로를 제거했다.
- 설치 후 앱을 **강제 종료하고 재실행**한다. 실행 중 모델 자동 교체는 하지 않는다.
- 다운로드 성공은 모델 추론 성공과 다르다. 실기기 필수 모델 게이트는 별도로 실행해야 한다.

배포처의 파일 메타데이터를 조회해 기존 런타임 해시와 같은 generic 아티팩트로 고정했다.
다른 최신 모델이나 칩셋 전용 모델로 바꾸지 않았다.

## 발견한 연결 문제와 수정

1. **갱신 무효화 유실**: 검색/이름 색인의 초기화가 진행되는 도중 저장 후 `invalidate()`가
   실행되면 구버전 초기화가 뒤늦게 캐시를 다시 채울 수 있었다. 초기화와 무효화를 같은 mutex로
   직렬화했다. 모델 기반 시험 대역으로 저장 후 새 카드가 보이는지 회귀 검증한다.
2. **검색 상태 혼용**: 색인 서비스와 model-backed 플래그를 따로 바꿨기 때문에 진행 중 검색이
   다른 턴의 초기화 상태를 읽을 수 있었다. 서비스·모델 상태·진단값을 한 불변 스냅샷으로 공개한다.
3. **이전 선택 명함 누출**: focus를 폐기할 때 `contact.selected_contact` 도구 상태도 제거한다.
   명시적 새 대상 검색은 과거 언급 이력에 같은 이름이 있더라도 이전 선택을 물려받지 않는다.
4. **중복 선조회와 native 프로토콜**: 일반 속성 조회는 이미 `ContactDetail`의 결정적 fresh-read
   경로가 있다. 모델 루프에 별도로 있던 `ownedDetailCall`은 사용자 입력 없이 도구 결과부터
   보내는 경로라 제거했다. 나머지 모델 루프는 항상 `model.decide(User)`로 시작한다.
   실기기 오류를 재현했다는 뜻은 아니며, 잘못된 메시지 순서를 만들 수 있는 구조를 제거한 것이다.
   또한 모델이 문장으로 답한 뒤 커널이 보완 실행한 선행 도구의 결과는 미요청 도구 응답으로
   보내지 않는다. NativeToolReplyTracker로 대기 중인 모델 호출을 확인하고, 커널 실행 결과는
   현재 요청의 자료로 전달한다. 요청/중복 응답/일반 답변/세션 초기화 경계를 시험한다.
5. **모델 상태 화면**: 엔진 이름의 `HYBRID` 문자열로 준비 상태를 추측하던 판정을 제거했다.
   임베딩 `동작 확인`은 실제 query 임베딩을 수행하며 실패 이유를 표시한다. 생성 모델의
   단순 진단 갱신 버튼은 `상태 확인`으로 구분했다. 임베딩이 없으면 키워드로 내려간다는 낡은 문구도 제거했다.
6. **동시 임베딩**: 검색·문서 갱신·상태 확인이 같은 native 임베더에 동시에 접근하지 않도록
   추론과 close를 직렬화했다. 필수 임베딩 실패 시 중단 정책은 유지한다.
7. **OCR 보완**: 방향 분류 세션의 SessionOptions 해제가 빠져 있어 use 범위로 관리한다.
   기존 OCR→동일 Room 행 저장→임베딩 갱신 완료 후 상세 화면 이동 연결은 유지했다.

## 검증 구분

- 다운로드의 HTTP 응답은 작은 테스트 파일과 시험 연결로 검증한다. 앱에서 2.8GB를 끝까지
  받고 실제 모델을 로드하는 검증을 대신하지 않는다.
- 테스트 대상: 정상 설치/재사용, 부분 다운로드, 해시 불일치 시 기존 파일 보존, HTTPS·인증
  리디렉션, 권한 거부, 가져오기 실패, 런타임-다운로드 해시 일치, 초기화 중 무효화,
  진행 중 검색의 스냅샷 일관성, 선택 상태 폐기, 이름 지정 조회→속성 후속 질문.
- 최초 선조회 회귀 테스트는 일반 속성 조회가 모델 경로를 타지 않아 목적한 분기를 검사하지
  못했다. 해당 테스트를 통과로 간주하지 않고 중복 선조회 제거 및 역할 순서 검증으로 정리했다.
- 최종 `gradlew test :app:assembleDebug :app:assembleDebugAndroidTest` 성공.
  JVM XML 합계 **520개, 실패 0, 오류 0, skip 0**(앱 debug 기준, release 중복 제외).
  변경 없는 태스크는 증분 결과를 사용했다. 로그: 로컬 `build/pipeline-final.log`.
- 마지막 추가 검색 경쟁 시험도 `:tool-contact:test`로 별도 통과했다.
- 엄격한 설치 스크립트는 로컬 모델 3개 SHA-256과 APK 필수 구성 12개 확인까지 성공했고,
  **연결된 arm64 실기기 0대에서 실패 종료**했다. 계측 테스트를 실행하거나 skip으로 통과시키지 않았다.
- 다운로드 소스 패키지 `models/`가 대형 모델 제외 규칙에 가려지는 것도 확인했다.
  `.gitignore`에 해당 Kotlin 소스 디렉터리만 예외를 추가해 새 clone에서 구현이 빠지지 않도록 했다.

## 아직 완료라고 할 수 없는 항목

- 실제 기기에서 사용자가 겪는 검색 실패 문장/연속 대화 재현.
- 필수 모델 전체를 탑재한 arm64 실제 추론 및 이번 변경의 Android 실행 검증.
- 모바일 네트워크에서 대형 파일 다운로드·화면 이탈·이어받기·저장공간 부족 실측.
- OCR 실제 촬영→저장→즉시 검색, 수정→재검색, 메일/일정 화면 복귀, 기존 v4 사용자 DB 검증.

필수 모델이 없거나 실제 기기가 없으면 완료 게이트를 중단한다. 키워드 폴백이나 JVM 시험
대역의 성공을 실제 모델 통과로 대체하지 않는다. 기기 연결 후 `scripts/install_real_device_debug.ps1`을 실행한다.
